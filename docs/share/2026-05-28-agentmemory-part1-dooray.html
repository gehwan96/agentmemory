AgentMemory를 아시나요?

karpathy의 llm-wiki.md

Andrej Karpathy는 LLM을 쓸 때 느끼는 불편함 하나를 정직하게 짚었다. 매번 "이 코드베이스는 이런 구조야, 이런 컨벤션을 써, 이 서비스는 이렇게 연결돼 있어"를 반복해서 설명해야 한다는 것. 그래서 그가 만든 패턴이 llm-wiki.md다.

"LLM이 관리하는 위키를 만들고, 새 정보가 들어올 때마다 LLM이 스스로 업데이트하게 한다. 사람은 소스를 골라주고, LLM은 요약·링킹·교차 참조의 보조 작업을 전담한다."
— karpathy / llm-wiki.md

구조는 세 계층이다. 사람이 소스를 넣으면 LLM이 위키를 갱신하고, 다음 질문 때 위키를 프롬프트 앞에 붙인다. 처음부터 다시 설명하지 않아도 된다.

규칙
스키마 문서 "어떤 정보를 어떻게 기록할지" — LLM이 위키를 관리하는 방식을 정의
위키
LLM이 관리하는 위키 마크다운 파일 묶음 — LLM이 자동으로 생성·갱신·교차 참조
소스
원본 소스 코드, 문서, 대화 — 수정하지 않는 원재료

RAG는 질문마다 원본 문서에서 답을 조합한다. 결과는 그때그때 사라진다. 다음 질문 때 다시 처음부터다. llm-wiki는 다르다. LLM이 만든 요약, 교차 참조, 맥락을 위키 페이지로 남긴다. 쓸수록 쌓인다. Karpathy는 이걸 persistent, compounding artifact라고 표현했다.

그럼 왜 사람은 이걸 직접 안 했을까. 귀찮아서가 아니다.
소스 하나를 추가하면 연관된 위키 페이지 10~15개를 동시에 고쳐야 한다. 이 갱신을 빠뜨리면 위키는 금방 낡고, 결국 아무도 믿지 않게 된다. 하지만 LLM은 이 작업을 실수 없이 해낸다.

RAG는 매번 답을 새로 만든다. llm-wiki는 그 답을 남긴다.
위키가 죽었던 건 의지 문제가 아니라 유지보수 비용이 감당 안 됐기 때문이다. LLM이 그걸 가져가면서 희망이 생겼다.

2llm-wiki의 한계 — 그래서 무엇이 더 필요한가

rohitg00의 llm-wiki v2는 이 패턴을 실제로 써보고 부딪힌 문제들을 솔직하게 정리한 글이다.

실제로 걸리는 세 가지

  • 소스 선별은 여전히 수동 — llm-wiki가 자동화한 건 위키 갱신이지, 소스 수집이 아니다. 어떤 문서를 위키에 넣을지는 사람이 직접 판단해야 한다. 실제 개발 흐름에서는 이렇게 무너진다: 코드 리뷰를 끝내고 "나중에 위키에 넣어야지" 하다가 안 한다. 그걸로 끝이다. 소스 선별이 사람 손에 달려있는 한, 위키는 개발 습관에 종속된다. 바쁘면 바로 죽는 구조다.
  • 검색 확장성 — 페이지가 200~500개를 넘으면 단일 index.md 방식으로는 적절한 정보를 꺼내오기 어려워진다. 키워드 매칭만으로는 의미 기반 검색이 안 된다.
  • 세션 간 자동 연결 없음 — 어제 한 작업의 맥락이 오늘 세션에 자동으로 주입되지 않는다. 위키를 프롬프트 앞에 붙이는 것도 결국 사람이 기억해서 해야 한다.

그가 원하는 것

rohitg00이 v2에서 요구한 것들을 한 줄씩 정리하면:

영역요구 사항
자동화세션 종료 시 자동 압축·저장, 새 이벤트마다 자동 수집
수명주기신뢰도 점수, 오래된 정보 자동 감쇠, 버전 관리
검색BM25(키워드) + 벡터(의미) + 그래프 탐색의 하이브리드
격리여러 프로젝트·작성자가 섞이지 않도록 프로젝트 단위 격리
보안민감 데이터 자동 제거, 삭제 감사 로그

llm-wiki가 자동화한 건 절반이었다. 위키 갱신은 LLM이 하지만, 무엇을 넣을지는 여전히 사람 몫이다. rohitg00이 원한 건 그 나머지 절반 — 소스 수집까지 자동화된 시스템이다.

마침 그 자동화 시도 중 하나가 AgentMemory다. llm-wiki를 대체한다기보다, 사람이 직접 적기 어려운 부분을 자동으로 메워주는 보완재에 가깝다.

영역 llm-wiki (수동) AgentMemory (자동)
작성 주체 사람이 직접 소스를 넣음 에이전트 훅이 자동으로 수집
갱신 시점 사람이 기억해서 실행할 때 매 tool 호출 + 세션 종료
회수 방식 위키 파일을 프롬프트에 붙여넣기 MCP 도구로 시맨틱 검색 + 자동 주입
강점 일관성·검증성 (사람이 검토함) 자동성·세션 연속성 (개입 없이 동작)
약점 유지보수 부담, 세션 연결 수동 자동 압축의 품질이 모델에 의존
여기서 한 가지가 걸린다. "아무것도 하지 않아도 기억이 쌓인다"는 건, 뒤집으면 검토하지 않은 정보가 자동으로 기억에 올라간다는 뜻이기도 하다. llm-wiki의 핵심 가치가 "사람이 검토한 정보만 남긴다"였던 걸 떠올리면, 자동 수집은 강점인 동시에 위험이다.
rohitg00이 v2에서 요구한 신뢰도 점수·자동 감쇠가 바로 이 지점을 겨냥한 것이고, AgentMemory도 메모리마다 confidence 값과 시간 감쇠(temporal decay)를 데이터 수명주기에 반영한다. 다만 그 자동 압축·감쇠가 정말 믿을 만한 기억을 남기는지는 써봐야 안다 — 그래서 2편에서 이 메커니즘을 직접 뜯어보고 검증한다.

3AgentMemory란?

AgentMemory는 Claude Code, Cursor, Codex 같은 AI 에이전트의 세션 간 기억을 지속시키는 MCP 서버다. (MCP는 AI 도구가 외부 기능을 표준 규격으로 끌어다 쓰게 해주는 연결 방식이다.) AI 에이전트는 세션이 끝나면 모든 맥락을 잊는다. 같은 프로젝트를 매번 처음부터 파악하는 낭비가 생기는 이유다. AgentMemory는 에이전트가 파일을 읽고, 명령을 실행하고, 결정을 내릴 때마다 발생하는 이벤트를 자동으로 수집·압축·저장한다. 다음 세션에서는 관련 기억을 꺼내 쓰며 맥락을 이어간다.

내부적으로는 4계층의 데이터 모델을 사용한다. Session(세션 단위 컨테이너) → RawObservation(실시간 이벤트 캡처) → CompressedObservation(LLM 압축 후 인덱싱) → Memory(장기 기억 — 영속 저장). 위로 올라갈수록 더 요약되고 오래 보존된다. 여기서는 이 흐름의 전체 그림까지만 잡는다 — 각 계층이 실제로 어떤 스키마로 저장되고 어떻게 인덱싱·검색·감쇠되는지는 한 편 분량이 필요할 만큼 핵심이라, 2편에서 따로 뜯어본다.

4어떻게 동작하나

에이전트가 일을 시작할 때부터 끝날 때까지, AgentMemory는 네 단계로 개입한다. (여기서 "훅(hook)"은 세션 시작·도구 호출·종료 같은 특정 시점에 미리 걸어둔 코드가 자동 실행되는 연결 고리를 뜻한다.)

1

세션 시작 — 과거 기억 주입

Claude Code가 세션을 열면 SessionStart 훅이 AgentMemory에 /session/start를 호출한다. INJECT_CONTEXT=true 설정이 켜져 있으면, 이 시점에 현재 프로젝트와 관련된 과거 기억을 자동으로 프롬프트에 주입한다. 사용자가 아무것도 하지 않아도 에이전트는 이미 "이 프로젝트를 아는 상태"로 시작한다.

2

작업 중 — 관련 기억 회수

사용자 프롬프트와 도구 호출이 일어나는 동안 에이전트는 memory_recall / memory_smart_search MCP 도구로 필요한 기억을 꺼낸다. BM25 키워드 검색과 벡터 시맨틱 검색을 결합한 하이브리드 방식이라 단순 키워드 매칭보다 정확하다.

3

작업 중 — 관찰 수집

PostToolUse, PostToolUseFailure 등 12개 훅이 모든 이벤트를 /observe로 전송한다. 중복 해시로 같은 이벤트는 걸러내고, 민감 데이터(토큰, 비밀번호 등)는 stripPrivateData()로 자동 제거한 뒤 KV 저장소에 쌓는다.

4

세션 종료 — 압축·저장

Stop 훅이 mem::summarize(map-reduce 요약)와 mem::compress(LLM 압축)를 호출한다. 이어서 SessionEnd 훅이 4단계 통합 파이프라인을 트리거해 단기 관찰을 장기 메모리로 증류한다. 각 단계가 하는 일은 한 줄로 이렇다 — Semantic Merge(여러 세션에 흩어진 사실을 안정된 지식으로 병합) → Reflect(2개 이상 기억에 걸친 패턴·원칙을 인사이트로 합성) → Procedural(반복된 작업에서 "이럴 땐 이렇게" 절차를 추출) → Graph(기억들 사이의 엔티티·관계를 시간 그래프로 연결). 각 단계의 내부 동작은 2편에서 자세히 다룬다.

세션이 끝나면 잊는 대신, 끝날 때 압축해서 다음 세션이 꺼내 쓸 수 있는 형태로 남긴다.
정상 종료(Stop 훅)가 중요하다. 강제 종료하면 압축·저장 단계가 실행되지 않아 그 세션의 관찰 데이터가 장기 메모리로 올라가지 않는다. Ctrl+C가 아니라 에이전트를 정상적으로 종료하는 습관이 기억의 품질을 좌우한다.

5기초 설치 가이드

세 단계면 연결까지 끝난다.

1) 서버 실행

npm install -g @agentmemory/agentmemory
agentmemory init       # ~/.agentmemory/.env 생성
agentmemory doctor     # 환경 변수 및 설정 점검
agentmemory start      # 포트 3111 (API), 3113 (웹 뷰어)

설치 없이 바로 쓰려면: npx @agentmemory/agentmemory

2) 환경 변수 설정 — ~/.agentmemory/.env

# AI 제공자 셋 중 하나만 설정 (아래 우선순위 순)
OPENAI_API_KEY=...
ANTHROPIC_API_KEY=...
GEMINI_API_KEY=...

# 기본 8개 도구 → 전체 54개 노출
AGENTMEMORY_TOOLS=all
API 키가 없어도 서버는 실행된다. 단, LLM 압축과 시맨틱 검색이 비활성화되어 키워드 기반 합성 압축만 동작한다.

3) Claude Code에 등록

agentmemory connect claude-code # MCP 서버 등록
agentmemory connect claude-code --with-hooks  # 훅(자동 수집)까지

동작 확인 체크리스트

✓http://localhost:3113 → 웹 뷰어가 열린다
✓agentmemory doctor → 모든 항목 ✓
✓에이전트에서 memory_sessions 호출 → 오류 없이 반환됨
✓AGENTMEMORY_TOOLS=all 후 재시작 → 도구 목록이 8개에서 54개로 늘어남

6그래서 쓸 만한가?

이건 코드를 뜯어본 분석 단계의 결론이다 — 몇 주 직접 굴려본 실사용 후기는 시리즈 뒤 편에서 이야기할 계획이다. 그 전제 위에서 지금 내리는 판단은, "단순 설치로는 효과를 보지 못할것 같다"이다.

"에이전트가 어제 한 일을 기억하게 한다"는 컨셉은 실용적이나 사용해본 결과 개인의 세션 사용 패턴, 압축 여부가 생각보다 중요해 보인다.

살짝 맛본 중간 후기론 agentmemory는 llm-wiki를 대체하진 않는다고 생각한다. 오히려 역할을 나누면 경계가 분명해지는 느낌이 든다. 틀리면 안 되는 정보(팀 합의 정책·검토된 결정)는 사람이 llm-wiki에, 일상 맥락·시행착오·세션 연속성은 agentmemory에 맡겨보면 어떨까? 라는 생각이 들어 조금 구조를 개선해 사용해보고자 한다. 구체적인 한계 및 개선 내용은 시리즈 뒤편에서 정리한다.

결론

완벽한 시스템은 아니다. 한계도 분명히 있다. 그러나 "설치하고 훅만 연결하면, 내일부터 에이전트가 기억을 가진 채 일을 시작한다." 이 컨셉을 도입하는 것은 꽤나 괜찮아 보인다.
